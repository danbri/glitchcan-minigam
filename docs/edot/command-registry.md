# edot Command Registry & Ontology (Phase 1)

Status: **Phase 1 shipped.** The registry + ontology foundation is live in the shell, with Slides migrated as the pilot. Remaining apps migrate lazily (Phase 2) using the per-app inventory tables in `docs/apps/`.

## What it is

Every side-effecting UI action is (becoming) a **named, typed command** in one shared registry, instead of a bespoke closure. This gives — uniformly — a command palette, programmatic invocation (Automations), contextual applicability, keyboard shortcuts, and a single audit/policy choke point.

The registry is tied to an **explicit ontology** (`js/ontology.js`): a command can declare `appliesTo: <EntityType>`, so the system knows which actions are relevant to which *kind* of thing (a `SlideElement`, a `Calendar`, a `Document`…). Widgets declare which type they edit. The whole vocabulary emits as RDF (Turtle).

| Piece | File | Notes |

## Command shape

```js
registry.register({
  id: 'slides.rotate', title: 'Rotate element 90°', icon: '⟳',
  group: '3arrange', keywords: 'rotate orient',
  appliesTo: 'SlideElement',                 // ontology type — only offered for an element
  when: (ctx) => ctx.app === 'slides' && hasSelection(),
  run: (ctx, args) => activeSlides.rotateActive(90),
});
```

- **`appliesTo`** filters via the ontology subclass relation: a `SlideElement` command is offered for `TextElement`/`ImageElement`/`ShapeElement`; a command with no `appliesTo` is global.
- **`when(ctx)`** gates contextual availability (and is re-checked in `run()`).
- **`run()`** is the choke point — `onAudit`/`onPolicy` hooks already exist for the future enterprise phase.

## How surfaces use it

- **Palette**: `registry.search(query, { app })` → list → `registry.run(id, ctx)`.
- **By entity type**: `registry.forType('ShapeElement', ctx)` → element + shape commands for a selected shape (this is the "which actions for this kind" relation, used directly).
- **Automations**: `edot.invoke('command.run', { id: 'slides.addSlide' })`.
