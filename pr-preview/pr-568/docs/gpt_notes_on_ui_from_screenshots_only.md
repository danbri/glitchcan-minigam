# UI Design Directions for a Distributed, Ink-Driven Choice Game Platform

This document defines a cohesive UI/UX design framework for a distributed, media-rich, multiple-choice narrative platform built on Inkle's Ink, JavaScript, and external media. The objective is a UI that is creative, usable, engaging, and stylistically distinctive, while remaining faithful to Ink's strengths: text-first narrative, conditional branching, and persistent state. The guiding metaphor is a "playable document" rather than a conventional game interface.

The core conceptual model treats every screen as a living page. Each page prioritises a single narrative column, with text as the primary carrier of meaning. Media elements such as images, audio, video, or scripted canvases are embedded inline within the narrative flow rather than floating as background wallpaper or appearing as modal interruptions. Choices are presented as part of the document structure itself, integrated visually and semantically with the text that precedes them. System elements exist, but they are deferential, clearly separated from the narrative voice, and never compete for attention. This approach aligns naturally with Ink's STORY → KNOT → STITCH → CHOICE hierarchy and supports scrolling, bookmarking, saving, and distribution without heavy UI scaffolding.

Typography is treated as a first-order design concern, particularly because sessions may involve extended reading. A dual-voice typography system is recommended. The narrative voice, used for story text, description, dialogue, and internal monologue, should use a highly readable serif or humanist font designed for long-form reading, with a generous x-height and moderate contrast. Suitable examples include Literata, Source Serif, IBM Plex Serif, Charter, or a robust system fallback such as Georgia. In contrast, the system voice, used for status messages, warnings, debug output, diagnostics, and meta UI such as missing-media notices or save/load affordances, should use a visually distinct monospace or pixel-inspired font. This establishes a clear separation between "story" and "machine". Fonts such as VT323, PxPlus IBM VGA, IBM Plex Mono, or JetBrains Mono work well here. Hierarchy rules should ensure that narrative text never looks mechanical, system text never disrupts reading rhythm, and choices visually sit between the two voices.

Choices themselves are the primary interaction mechanism and should feel intentional rather than mechanical. Traditional large, brightly coloured buttons tend to push the interface toward a conventional game aesthetic and encourage rapid clicking. Instead, choices should be rendered as intent signals or choice rows that read naturally as part of the document. Examples include prefixed lines such as "› Step onto the platform, heart pounding", "→ Linger in the doorway, scanning the crowd", or "⚑ Watch a snowflake land on her glove". Each choice should occupy a full-width tappable row with generous vertical spacing, subtle separators instead of hard borders, and restrained iconography. Optional enhancements include light-weight intent tags indicating emotional tone or risk, soft conditional indicators such as faded locks or question marks, and the ability to ghost previously chosen options in the margin as echoes. On mobile, the entire row should be tappable with no reliance on hover states and no small hit targets.

Media integration should be handled through contextual framing rather than decoration. Images, video, audio, or interactive canvases should appear in framed context panels that feel authored and intentional. These panels can include captions that are either diegetic, meta-commentary, or system-level notes, and may use subtle borders, glows, or grain overlays derived from the active theme. Media should scroll naturally with the text. Video should never auto-play with sound. Audio should be associated with the scene rather than with explicit tracks, reinforcing atmosphere without demanding attention. Scripted or canvas-based elements should behave like illustrations or diagrams embedded in the document, not as separate mini-games competing for focus.

Audio design benefits from a scene-based model rather than a playlist-based one. Each scene defines an audio profile consisting of a base ambience and optional layered effects, along with transition rules such as fades or crossfades. The UI representation of audio should be minimal and ideally diegetic, for example a small lantern, rain, or waveform icon indicating that ambience is active. Controls should be limited to muting or adjusting ambience intensity. Audio should generally persist across choices and only change when the narrative context changes.

State and progress feedback should be soft, peripheral, and largely implicit, reflecting Ink's strength in conditional logic and hidden variables. Loud meters, constant numerical counters, and prominent gamified dashboards should be avoided. Instead, state can be communicated narratively through short textual cues such as "You feel watched", "Something has changed", or "You are carrying a secret". Quantitative information such as inventory counts or scores can be available on demand via a collapsible ledger or notebook panel, but should not dominate the main reading experience. Saving and resuming should feel like placing or returning to a bookmark rather than loading a conventional save slot.

Because the platform is distributed, world and episode navigation must be treated carefully. The home or hub view should present worlds as tangible artefacts such as books, cassettes, files, or letters, with episodes represented as chapters or inserts and save states as bookmarks or dog-eared pages. Transitioning between worlds should be an intentional narrative act, explicitly acknowledged by the UI with confirmation language such as "You leave this story behind", accompanied by a visual transition like a paper fade, CRT power-down, or fog dissolve.

A creator-facing visual theming system is essential to support diverse aesthetics without code changes. Themes should be defined declaratively and control variables such as narrative and system font pairs, accent colours, border styles, grain or noise levels, choice animation styles, and background textures. This allows radically different looks—noir, fantasy, sci-fi, cosy, archival, or terminal-punk—to coexist on the same underlying engine.

Accessibility must be treated as a core requirement rather than an afterthought. Essential features include font size controls, high-contrast mode, reduced-motion mode, screen-reader-friendly choice lists, and an option to always display choice numbers. Additional enhancements such as dyslexia-friendly font toggles, adjustable line spacing, and audio descriptions for media further improve inclusivity and also aid debugging and testing.

Finally, the platform should include a small number of distinctive interaction ideas that give it a recognisable identity. Examples include choice echoes where past decisions linger faintly in the margins, temporal text effects that suggest typing or handwriting, memory scars where the UI subtly shifts colour or texture based on accumulated decisions, diegetic menus that appear as notebooks, radios, or terminals, and narrative glitches that visually manifest unreliable narrators or fractured timelines. Taken together, these elements should make the experience feel like reading a strange book that responds, browsing a haunted or living document, and making deliberate, thoughtful decisions where media deepens mood without overpowering text.
